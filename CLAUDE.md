# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A Unity 2D game project (working title "超人貓大亂鬥" / "Super Cat Brawl"). Unity Editor version **2022.3.62f3**. The project has a working combat loop: two playable characters (SuperCat, RedSuperCat), each with three functioning skills, and one enemy (DogeEnemy) with a continuous 0–5 difficulty scale and a two-phase attack pattern, playable in `Assets/Scenes/Battle.unity`. A shared status-effect system (stun/slow/curse/target-lock, see "Debuff / crowd-control system" below) and a win/lose results flow (`BattleResultUI`) are both wired up.

## Development environment

This is a Unity project, not a CLI-buildable package — there are no npm/dotnet CLI build, lint, or test commands to run from the terminal. Building, running, and testing happen inside the Unity Editor:

- Open the project via Unity Hub with Editor version `2022.3.62f3` (see `ProjectSettings/ProjectVersion.txt`).
- Play mode in the Editor (on `Assets/Scenes/Battle.unity`) is the primary way to run and manually test the game.
- The `com.unity.test-framework` package is installed, so Unity Test Runner (Window > General > Test Runner) is available for EditMode/PlayMode tests, but no test assemblies exist yet.
- C# scripts target `netstandard2.1` / `LangVersion 9.0` (see `Assembly-CSharp.csproj`). The `.sln`/`.csproj` files are Unity-generated — treat them as build artifacts, not hand-maintained project files.
- Do not edit files under `Library/`, `Temp/`, `Logs/`, `UserSettings/`, or `obj/` — these are Unity-generated caches, not source.

## Inspector-wired references

Don't defensively null-check `[SerializeField]` references that are supposed to be wired in the Unity Inspector (UI `Image`/`Text` fields, cross-component references like `BattleResultUI`'s reference to `RivalDialogueManager`, etc.) — no `if (x == null) return;`/`?.` guards around them. Dereference them directly so a forgotten wire-up throws a `NullReferenceException` immediately, with a stack trace pointing at the exact field that's missing — that's the fastest way to find it. Silently no-op'ing instead hides the mistake behind several layers of "nothing happens," which is much slower to debug (this is exactly what made the `BattleResultUI.rivalDialogueManager` wiring gap take several rounds of `Debug.Log` tracing to find instead of one Console error). Reserve real null checks for genuinely optional, per-level *content* rather than structural wiring — e.g. `LevelData.rivalDialogueScript` being unset because a level intentionally has no rival dialogue is a legitimate absent-by-design state, not a mistake, so that one should still degrade gracefully.

## Code architecture

Gameplay scripts live under `Assets/Script/`, split into `Player/`, `Enemy/`, `Level/`, `UI/`, and `Common/`.

### Stats/skill composition pattern (players)

- `Assets/Script/Player/PlayerBase.cs` — `PlayerBase : MonoBehaviour, IDamageable, IKnockbackable` is the shared base for all playable characters. Requires `Rigidbody2D`, `CircleCollider2D`, `SpriteRenderer`, `Animator`. It holds a `PlayerStats` instance and three skill slots (`normalAttack`, `dashSkill`, `ultimateSkill`), each typed as `ISkill`. `Update()` reads WASD movement input, tracks `FacingDirection`, flips the sprite, and (unless `IsKnockedBack`/`IsStunned`) drives all three skills' `TryExecute()` every frame — `IsCursed` additionally blocks `dashSkill`/`ultimateSkill` only, normal attack still fires (see "Debuff / crowd-control system" below for what stun/curse are); `FixedUpdate()` applies movement (unless a skill is mid-movement via `IsActive`, or the player is `IsKnockedBack`/`IsStunned`), ticks dash/ultimate, ticks the shared `KnockbackState` (see `EnemyBase`/"Shared/common" for what that is), and ticks the player's `PlayerDebuffState`. Wall collisions call `Interrupt()` via `OnCollisionEnter2D`; enemy hits call `OnHitEnemy()` on both movement skills via `OnTriggerEnter2D` — enemy colliders are triggers (see `EnemyBase.Awake`), so the two sides no longer physically collide/push each other, only walls remain a solid `OnCollisionEnter2D`. `CanBeKnockedBack => !ultimateSkill.IsActive` gates `TryKnockback` **and** `TryApplyStun` — the ultimate's dash invulnerability deliberately blocks both, not just damage. `TakeDamage` is instead gated by a separate virtual `IsDamageImmune` (defaults to `forcedInvincible || !CanBeKnockedBack`, so SuperCat's ram is immune-to-both-by-default) — the two were split apart specifically so a future skill can be "uninterruptible but still takes damage" without touching the knockback gate; `forcedInvincible` is an external toggle (`SetForcedInvincible`) used only by the victory flow below. A successful `TryKnockback`/first-application `TryApplyStun` interrupts `dashSkill`/`ultimateSkill` the same way a wall hit does, so an incoming knockback/stun always wins over an in-progress skill move. Also exposes read-only properties (`Health`, `MaxHealth`, `S1_Cooldown(Current)` for the dash slot) and a **generalized ultimate-progress pair** `S2_Cooldown`/`S2_CooldownCurrent` that just forwards to `ultimateSkill.Cooldown`/`CooldownCurrent` — this lets `UIManager` read one property pair regardless of whether the character's ultimate is charge-gated (SuperCat's `ChargeRamSkill`, which reports the shared `PlayerStats.Charge` through those properties) or purely cooldown-gated (RedSuperCat's `RadialBurstSkill`). The virtual `S2_ShowSecondsFormat` (default `false`) tells `UIManager` whether to render that pair as "current/max" (charge-style) or as remaining seconds (cooldown-style) — see `UIManager.UpdateS2` below.
  - **Death/results hooks (used by `BattleResultUI`, see "UI" below)**: `IsDead` goes `true` the instant `Health` hits 0 and from then on `Update`/`FixedUpdate` both bail out immediately — position/animation are handed off to `BeginDeathSequence(targetPosition, duration)`, which plays the `KB` trigger and `Lerp`s the `Rigidbody2D` to a camera-relative death pose over `duration` via a coroutine (`DeathMoveRoutine`), ignoring whatever knockback direction actually killed the player. `SetSuppressNormalAttack(bool)` stops only the normal attack (movement/other skills keep working) and `SetForcedInvincible(bool)` forces `IsDamageImmune` — both are used by the victory sequence so the player can still walk around while looking invulnerable and holstered.
- `ISkill` (defined in `Assets/Script/Player/Skills/SkillBase.cs`) is the contract every skill implements: `Cooldown`, `CooldownCurrent` (progress toward ready, for UI), `CooldownMultiplier` (get/set, default 1 — external code, currently only `PlayerBase.ApplyDebuffCooldownEffects` reacting to slow, scales `Cooldown`; skills without a real time-based cooldown, like `ChargeRamSkill`, expose it as a no-op backing field since nothing reads it), `TryExecute()`, `IsActive`, `Tick()`, `Interrupt()`, `OnHitEnemy(Collider2D)`, `ReduceCooldown(float seconds)` (external cooldown reduction — a positive value shortens the wait for a passive on-hit effect, a *negative* value lengthens it, which is how `PlayerBase` implements stun: it calls `ReduceCooldown(-Time.fixedDeltaTime)` on all three slots every physics step while stunned so `Cooldown` progress is frozen rather than ticking). Skills that involve a movement/dash phase (dash, ultimate) use `IsActive`/`Tick()`/`Interrupt()`/`OnHitEnemy` to drive their own `Rigidbody2D.MovePosition` during `FixedUpdate` while suppressing normal WASD movement; instant-effect skills (normal attack) implement these as no-ops. Not every "busy" skill sets `IsActive`, though — `BarrageSkill`/`RadialBurstSkill` (see RedSuperCat below) deliberately leave `IsActive => false` so WASD movement stays available while they fire, and expose their own `IsFiring`/`IsSpinning` bool instead for other skills to query/suppress against. Skills are independent, swappable classes (composition over inheritance) — a character is assembled by wiring concrete `ISkill` implementations into the base's skill slots in `Awake()`, not by subclassing behavior.
- `IDamageable` (defined in `PlayerBase.cs`) is the contract for anything that can take damage (`TakeDamage(float amount)`); implemented by both `PlayerBase` and `EnemyBase`. `IKnockbackable` (also in `PlayerBase.cs`) is the parallel contract for anything that can be pushed back (`TryKnockback(Vector2 direction, float distance)`); also implemented by both. Attack code should target these two interfaces rather than the concrete `PlayerBase`/`EnemyBase` types, so the same attack logic works regardless of which side is being hit.
- `PlayerStats` (also in `PlayerBase.cs`) is a plain data class holding `baseAttack`, `baseHealth`, `moveSpeed`, `Health`, `healthRegenMultiplier` (per-character regen tuning, defaults to 1), and a shared **charge** resource (`Charge`, capped at the const `MaxCharge`) with `AddCharge`/`SpendCharge` — charge is spent by ultimates that opt into it (only `ChargeRamSkill` currently) and earned via normal-attack hits (`Bullet` grants +1 on enemy hit when `owner is PlayerBase`). `TickRegen(deltaTime, levelMultiplier)`, called every `Update()` from `PlayerBase` (skipped while paused/dead), auto-heals at `baseHealth * 1% * healthRegenMultiplier * levelMultiplier` HP/sec once `Health` is below max — converted internally into "heal 1 point every N seconds" so it doesn't lose fractional HP to `float` truncation; `levelMultiplier` comes from `LevelManager.RegenLevelMultiplier` (see "Level framework" below), so regen gets weaker as difficulty rises.
- `Assets/Script/Player/SuperCat.cs` is the original character: subclasses `PlayerBase`, and in `Awake()` wires up `AutoLockShootSkill` (normal attack), `DashSkill` (dash), and `ChargeRamSkill` (ultimate) — all under `Assets/Script/Player/Skills/`.
- `Assets/Script/Player/RedSuperCat.cs` ("赤井抄太郎") is the second character: a glass-cannon bullet-hell archetype with **no movement skill** — both `dashSkill` and `ultimateSkill` slots are filled with firing skills instead (`BarrageSkill`, `RadialBurstSkill`), so it never gets dash-invulnerability or repositioning. Its passive (`OnProjectileHit`, wired as every skill's `onHit`/`onProjectileHit` callback) shortens both `BarrageSkill`'s and `RadialBurstSkill`'s cooldowns by a flat amount whenever any of its bullets — normal attack, `BarrageSkill`, or `RadialBurstSkill` — hits an enemy *or* destroys an enemy bullet (all three fire `Destructive` bullets, so bullet-vs-bullet kills count too). Overrides `S2_ShowSecondsFormat => true` since its ultimate is pure-cooldown, not charge-based.
- Player-facing values (attack/health/moveSpeed) are currently hardcoded per-character in `Awake()` rather than driven by a leveling system, though `RedSuperCat` derives its Lv1 numbers from an explicit `baseValue * (10 + level)` growth formula (commented inline) as a placeholder for that future system.
- Skill implementations follow a click-toward-cursor convention: on mouse-button-down, direction is computed straight from the owner's position to the mouse's world position (via `Camera.main.ScreenToWorldPoint`) — there is no drag tracking. `DashSkill` triggers on left-click and is gated by a cooldown, and deals no damage (pure movement). `ChargeRamSkill` triggers on right-click, is gated by charge cost instead of a cooldown (reports `PlayerStats.Charge`/`MaxCharge` through `CooldownCurrent`/`Cooldown` — see the `S2_*` forwarding above), and grants **full damage immunity** (via `IsDamageImmune`) while `IsActive`; on hit it deals damage and also calls `IKnockbackable.TryKnockback` with the charge direction and a large knockback distance (a "movement-based" melee hit — the attacker's own body moves into the target, as opposed to a stationary hitbox swing; see `MeleeHitbox` below for that alternative). `BarrageSkill` (RedSuperCat's dash slot) triggers on left-click, locks a direction once toward the cursor, then fires a 5-bullet fan (`Destructive`) centered on that locked direction — the first bullet fires immediately, the rest follow at `bulletInterval` — spread `angleBetweenDegrees` apart and evenly split left/right of center, exposing `IsFiring` while doing so; triggering also resets the normal attack's own cooldown (via an `onTrigger` callback wired in `RedSuperCat.Awake`) so the fan and normal-attack auto-fire don't visually double up right as the fan ends; `AutoLockShootSkill`'s own auto-fire is suppressed while `BarrageSkill.IsFiring` or `RadialBurstSkill.IsSpinning` (via its optional `isSuppressed` constructor param) so RedSuperCat doesn't fire three streams at once. `RadialBurstSkill` (RedSuperCat's ultimate) triggers on right-click, interrupts `BarrageSkill`, locks onto the nearest enemy once at trigger time, then spins the character's sprite one full clockwise rotation over `spinDuration` while firing 20 bullets in sequence as the rotation sweeps past each bullet's angle — those bullets are mildly homing (`Bullet`'s `homingTarget`/`homingTurnRateDegrees`/`homingDuration` params, see `Bullet.cs` below) toward the locked target and give up tracking (reverting to straight-line flight) after `homingDuration` seconds if they haven't hit. Both new skills play SFX through `AudioManager` the same way the originals do (trigger/cooldown-block "no"/cooldown-ready "skill_done").

When adding a new playable character, follow the `SuperCat`/`RedSuperCat` pattern: subclass `PlayerBase`, and in `Awake()` assign concrete `ISkill` implementations to `normalAttack`, `dashSkill`, and `ultimateSkill` — a skill doesn't have to match its slot's original intent (RedSuperCat puts firing skills in the dash/ultimate slots), the slots just control turn order and which `Interrupt()`/`OnHitEnemy()` calls target it. When adding a new skill, implement `ISkill` as an independent class (not a `MonoBehaviour`) that takes the owning `PlayerBase` and its tuning parameters via constructor, matching the existing `AutoLockShootSkill(this, bulletPrefab, damageMultiplier: ...)` call-site style.

### Debuff / crowd-control system

Shared status-effect layer that either side can apply to the other (no skill currently applies any of these — the plumbing exists ahead of the first skill that spends it). `DebuffType` (`Assets/Script/Common/DebuffType.cs`) is one enum — `Stun`, `Slow`, `Knockback`, `Curse` (player-only), `TargetLock` (enemy-only) — shared by both sides specifically so a single icon-display prefab/lookup table works for either; a side simply never calls the `Apply*` for a type that doesn't apply to it.

- **Per-side timer state**: `PlayerDebuffState` (`Assets/Script/Player/PlayerDebuffState.cs`) and `EnemyDebuffState` (`Assets/Script/Enemy/EnemyDebuffState.cs`) are plain (non-`MonoBehaviour`) classes held via composition — one instance each on `PlayerBase`/`EnemyBase`, same pattern as `KnockbackState`. Each effect has its own independent timer; re-applying while already active only **extends** the remaining duration (magnitude/multiplier never stacks). Both expose a `Tick(deltaTime)` the owner calls every `FixedUpdate`, and both funnel knockback's start/end through `NotifyKnockbackApplied`/`NotifyKnockbackEnded` purely for icon display — the actual stagger/displacement still runs through the owner's own `KnockbackState`/`TryKnockback`, this class never touches physics.
  - **Stun** (`IsStunned`): freezes input — `PlayerBase.Update`/`FixedUpdate` and `EnemyBase` subclasses are expected to check it up front, same as `IsKnockedBack`. Reuses the `CanBeKnockedBack` immunity gate (an uninterruptible attack like Doge's big bark or SuperCat's ram can't be stunned either), and the first from-nothing application interrupts the owner's current skill/action the same way a wall hit does (`ApplyStun` returns whether this was that first application, so the caller — `PlayerBase.TryApplyStun`/`EnemyBase.TryApplyStun` — knows whether to call `Interrupt()`/`InterruptCurrentAction()`).
  - **Slow**: has no immunity gate. Exposes a flat `MoveSpeedMultiplier` (0.5×) and a cooldown-side multiplier the owner is expected to read every frame — `SkillCooldownMultiplier` on the player side (written into all three `ISkill.CooldownMultiplier`s by `PlayerBase.ApplyDebuffCooldownEffects`) and `CooldownTimeMultiplier` on the enemy side (`DogeEnemy.Update` divides its own hand-rolled timers by it directly, since enemies don't have an `ISkill` cooldown to plug into).
  - **Curse** (player-only, `IsCursed`): no immunity gate. Blocks `dashSkill`/`ultimateSkill` triggering (`PlayerBase.Update` — normal attack is unaffected) and applies a constant downward drift to movement via `ApplyCurseToVelocity(rawVelocity)` — horizontal and downward input pass through unchanged, upward input is heavily damped (`curseUpwardInputMultiplier`) and an accelerating fall speed (`curseFallAcceleration` up to `curseMaxFallSpeed`) is subtracted from `y`; `PlayerBase.FixedUpdate` additionally clamps the resulting position to `LevelManager.Instance.GroundY` so a cursed player can't fall through the floor. Tuned via three `[SerializeField]` fields on `PlayerBase` (`curseFallAcceleration`/`curseMaxFallSpeed`/`curseUpwardInputMultiplier`), not on `PlayerDebuffState` itself.
  - **Target lock** (enemy-only, `HasTargetLock`/`TargetLockPosition`): the one non-stacking, non-immunity-gated effect — re-applying while already active is a no-op (position and remaining time both frozen at whatever the first call set). Freezes an enemy's aim at a fixed world position instead of tracking the player live; `DogeEnemy.GetTargetPosition()` is the single choke point every aiming call (`JumpRoutine`, `BiteRoutine`) goes through, so a new attack just needs to call that helper rather than reading `player.position` directly to automatically respect target lock.
- **Icon display**: `DebuffIconStack` (`Assets/Script/Common/DebuffIconStack.cs`) is the shared display-stacking logic both `PlayerDebuffState`/`EnemyDebuffState` hold one of (composition again). Rule: at most one icon shown at a time — always the most-recently-applied effect that's still active; when that one expires, display reverts to the next-most-recent still-active effect, and the icon `GameObject` itself is only `Instantiate`d on the first effect and `Destroy`ed when the last one ends (same "spawn on trigger, not pre-placed" style as `hitEffectPrefab`). The prefab (`debuffIconPrefab`, wired per-character/per-enemy in the Inspector, offset by `debuffIconLocalOffset`) must carry a `DebuffIconDisplay` (`Assets/Script/Common/DebuffIconDisplay.cs`) component with one child `GameObject` per relevant `DebuffType` wired in; `Show(type)` just `SetActive`s the matching child and hides the rest — a prefab can leave slots for types that don't apply to it (e.g. a player-side prefab has no `TargetLock` child) since `Show` silently no-ops on an unwired type.
- **Public API**: both `PlayerBase` and `EnemyBase` expose `TryApplyStun(duration)`, `TryApplySlow(duration)` (and `TryApplyCurse(duration)` player-side / `TryApplyTargetLock(position, duration)` enemy-side), each returning whether it was accepted (`false` only if the target is already dead, or — stun only — currently immune via `CanBeKnockedBack`). These live directly on the concrete base classes, not on `IDamageable`/`IKnockbackable` — since the two sides support different effect subsets (`Curse` vs. `TargetLock`), there's no shared interface for them yet; a skill that needs to apply one currently has to know which side it's hitting.

### Enemies

- `Assets/Script/Enemy/EnemyBase.cs` — shared base: `health`, `baseAttack`, `MaxHealth`/`HealthRatio` (captured from `health` in `Start()`, after difficulty has been applied), `IsDead`, `TakeDamage`, `IsKnockedBack`, `TryKnockback(Vector2 direction, float distance)` (fails if dead/`CanBeKnockedBack` returns false/already knocked back). Knockback/stagger state itself lives in a shared `KnockbackState` instance (composition, not inheritance — see "Shared/common" below) that both `EnemyBase` and `PlayerBase` hold independently; `EnemyBase.FixedUpdate()` ticks it (and the enemy's `EnemyDebuffState`, see "Debuff / crowd-control system" above) every physics step, which is what actually moves the Rigidbody2D during the knockback window and counts down the stagger timer (sourced from the defender's own `knockbackDuration` field — the attacker only controls direction/distance, never how long the stagger lasts). Subclasses override `CanBeKnockedBack` to make specific attacks uninterruptible, override `InterruptCurrentAction()` to actually stop whatever coroutine is running (base implementation is a no-op — called on both a successful knockback and stun's first application), must check `IsKnockedBack`/`IsStunned`/`IsDead`/`IsPaused` at the top of their own `Update()`/`FixedUpdate()` overrides, and **must call `base.FixedUpdate()`** in any `FixedUpdate()` override — skipping it silently breaks knockback/debuff ticking for that enemy. `IsPaused`/`SetPaused(bool)` is an external kill-switch used only by `LevelManager.PauseAllEnemies` (see below) once the player has died, so a defeated player doesn't keep eating hits while the results screen plays.
  - **Difficulty**: `ApplyDifficulty(int difficulty)` is a continuous 0–`MaxDifficulty` (5) scale, not discrete tiers — `health`/`baseAttack` at the moment `ApplyDifficulty` is called are treated as the difficulty-0 baseline, then multiplied by `healthMultiplier`/`attackMultiplier` raised to the difficulty (so the curve is exponential, not linear); `MaxDifficulty` gets one extra multiplier applied on top, to widen the gap at the very top of the range. Both multipliers and the difficulty-0 baseline are per-prefab `[SerializeField]` fields. `ApplyDifficulty` is only safe to call once per enemy instance — a second call would multiply on top of the already-scaled result. Subclasses override it to call `base.ApplyDifficulty(difficulty)` first, then layer their own difficulty-scaled parameters on top (`DogeEnemy` linearly interpolates its attack-cycle cooldowns between explicit difficulty-0/difficulty-5 values instead, rather than using the same exponential curve — see below).
  - **Death**: `TakeDamage` sets `IsDead`, `StopAllCoroutines()`s (so an in-progress attack is cut off immediately, not left to finish), sets the `isDeath`/`KB` animator params, then runs `DeathFadeRoutine` — waits `DeathFadeDelay`, plays the `"death"` SFX, then fades the `SpriteRenderer` alpha to 0 over `DeathFadeDuration`. The GameObject is never destroyed by this — it's left inert/invisible in the scene (relevant if anything ever needs to re-query dead enemies by tag).
  - Also defines a virtual `SetGroundBounds(Vector2 min, Vector2 max)` for ground-walking enemies to store their wander/chase rectangle; enemies that don't need a floor (e.g. flying) can ignore it. Requires `Rigidbody2D` (kinematic, no gravity), `CircleCollider2D` — `Awake()` sets it to `isTrigger = true`, so enemies no longer physically collide with the player or each other; contact damage must be detected via `OnTriggerStay2D`/`OnTriggerEnter2D`, not the `OnCollision*` family — and `SpriteRenderer`.
- `Assets/Script/Enemy/DogeEnemy.cs` subclasses `EnemyBase` and is the only enemy with real behavior: it wanders/chases within the rectangle set via `SetGroundBounds` (stored in the inherited `groundMin`/`groundMax` fields — `LevelManager` computes and assigns this at spawn time, see below) and cycles through attacks on a timer — a jump attack normally, or a horizontal "bite" (`BiteRoutine`) instead when the player is hiding below `biteThresholdY` where the jump's arc can't reach; both aim via `GetTargetPosition()`, which returns the frozen `TargetLockPosition` while `HasTargetLock` is true and the player's live position otherwise (see target-lock in "Debuff / crowd-control system" above). Once health drops at/below `phase2HealthPercent` of max, it gains a second-phase "big bark" attack (`BigBarkRoutine`) and is uninterruptible (`CanBeKnockedBack => !isBigBarking`, which also blocks stun) for its whole duration including repositioning; the phase-2 cooldown timer (`bigBarkCooldownTimer`) counts down continuously in `Update()` regardless of `isPerformingAction`/`IsKnockedBack` (frozen only while `IsStunned`, and slowed by `CooldownTimeMultiplier` while slowed) — it's only the *trigger* that waits for those to clear, so a jump/bite/stagger overlapping the cooldown's expiry doesn't add extra delay before the next big bark. Its `ApplyDifficulty` override calls `base.ApplyDifficulty` (health/attack), linearly interpolates its own attack-cycle cooldowns (`phase1CycleInterval`, `phase2CycleInterval`) between explicit difficulty-0/difficulty-5 `[SerializeField]` values, and stashes the raw `difficulty` int for `JumpRoutine` to read later — below `MaxDifficulty` the jump's peak height is capped at a hardcoded world-y (`maxJumpPeakYBelowMaxDifficulty`); at `MaxDifficulty` the cap is lifted. Long attacks run as coroutines and set `isPerformingAction` to suspend wandering/attack-cycle logic while they play; contact damage against the player (covering bite, jump, and plain wandering collisions alike — there's no separate per-attack damage path) is handled in `OnTriggerStay2D` (enemy colliders are triggers, see `EnemyBase.Awake` above), rate-limited by `bodyContactDamageInterval`, and applies a minor knockback via `IKnockbackable.TryKnockback` using the horizontal-only direction from Doge to the player (`contactKnockbackDistance`) — vertical component is deliberately zeroed so a jump landing doesn't launch the player up/down.
  - **Big bark (`BigBarkRoutine`)**: repositions to map-bottom-center facing the player, then fires `bigBarkRounds` rounds of bullets via `Bullet.Spawn` (plain `Bullet`s, targeting `"Player"` — there is no dedicated projectile class for this attack anymore, see below), each round preceded by a charge beat (`bigBarkChargeDuration` for round 1 with the mouth-open/close chatter animation, `bigBarkRoundInterval` for the rest with no mouth animation, plus an independent `BarkBlipRoutine` mouth-flash at every launch). Each round's `SpawnBigBarkRound()` lays out `bulletsPerGroup`-bullet clusters (`smallSpacingDeg` apart within a cluster) spaced `bigSpacingDeg` apart, sweeping world-space angles from a small random starting offset up through 180° — a fan-of-clusters volley across roughly half the circle rather than one aimed shot per round; angles are absolute, not relative to Doge's facing.

New enemies should subclass `EnemyBase` the way `DogeEnemy` does, rather than implementing `IDamageable` directly. `ApplyDifficulty`/`SetGroundBounds` are called by `LevelManager` immediately after `Instantiate` (i.e. during `LevelManager.Awake()`), which is guaranteed to run before the new enemy's own `Start()` — never before its `Awake()` finishes. There is no dedicated `SonicWave` projectile class anymore (it was deleted; the old `SonicWave.prefab` now just carries a `Bullet` component) — a new enemy's ranged attack should go through `Bullet.Spawn` the way `DogeEnemy`'s big bark does, rather than inventing a bespoke `MonoBehaviour` projectile, unless the attack genuinely needs custom shape/collision `SonicWave` used to provide.

### Level framework

- `Assets/Script/Level/LevelData.cs` — a `[CreateAssetMenu]` `ScriptableObject` holding everything that varies per level: `levelId` (stable string key, e.g. `"1-1"` — used by `StoryManager` as the `PlayerPrefs` key for "seen this level's story"; deliberately separate from `levelName` since that's player-facing display text that can be renamed without breaking save data), `levelName` (shown as the enemy-group health bar's label), `preBattleStoryScript` (optional `TextAsset` — see "Story system" below), `mapWidthMultiplier`/`mapHeightMultiplier` (map half-extent = one "base" screen-sized half-extent × these — see `LevelManager.GetBaseHalfExtent()` below), `groundHeightPercent` (the bottom N% of the map counted as ground for `SetGroundBounds`), `playerSpawnPosition`, `enemyPool` (a `List<EnemySpawnEntry>`, each an enemy prefab + spawn position — spawned once, all at level start; no wave system yet), `bgmName`, and `backgroundTilePrefab`. Difficulty is deliberately **not** part of `LevelData` — the same level can be replayed at any difficulty, so it lives on `LevelManager` instead.
- `Assets/Script/Level/LevelManager.cs` — replaces the old `BattleManager`; it's the scene entry point for `Battle.unity` and does all level setup in `Awake()` (in order: reposition the four `Wall`-tagged boundary objects found via `GameObject.FindGameObjectsWithTag("Wall")` — classified as horizontal/vertical by comparing `|x|` vs `|y|`, only their position is changed since their colliders are already oversized (100 units) to cover any reasonable map size — then tile the background, then instantiate the player at `playerSpawnPosition`, then instantiate each `enemyPool` entry and call `ApplyDifficulty`/`SetGroundBounds` on it, then wire up the camera). `GetBaseHalfExtent()` derives "1 map multiplier unit" from `Camera.main.orthographicSize`/`aspect` at runtime rather than a hardcoded constant, so a multiplier of 1 always means exactly one screen's worth of space regardless of resolution/aspect ratio — do not reintroduce a fixed half-width/half-height constant here, it will silently drift from the real screen the moment aspect ratio changes. Exposes a static `Instance`, `LevelName`, `GroundY` (the map's bottom world-space y, same value fed into ground-enemy `groundMin.y` — also what a cursed player's fall gets clamped to, see "Debuff / crowd-control system" above), and `EnemyGroupHealthRatio` (current pooled health ÷ the total health captured right after `ApplyDifficulty` at spawn time — a fixed denominator, so killing an enemy visibly drops the bar instead of the ratio re-basing itself). `Update()` sets `LevelCleared` true (and stops re-checking) the first time every spawned enemy's `IsDead` is true; `BattleResultUI` (see "UI" below) polls that flag to drive the win flow, and `PauseAllEnemies(bool)` — called by `BattleResultUI` at the start of both the victory and defeat sequences — flips every spawned enemy's `IsPaused` so AI stops acting once a result has been triggered (mainly matters for defeat, since victory only fires once every enemy is already dead). Difficulty is a `[SerializeField, Range(0, EnemyBase.MaxDifficulty)] int difficulty` field on `LevelManager` itself (continuous 0–5, matching `EnemyBase.ApplyDifficulty`'s scale — not the old discrete enum), currently a placeholder manually set in the Inspector until a level-select/difficulty-select flow exists to pass it in; `RegenLevelMultiplier` looks that same field up in a fixed `regenLevelMultiplierByDifficulty` array (higher difficulty → lower multiplier) and feeds `PlayerStats.TickRegen` (see "Stats/skill composition pattern" above), so auto-regen gets weaker as difficulty rises.
- `Assets/Script/Common/CameraFollow.cs` — added at runtime by `LevelManager` (via `AddComponent`, so it never needs to be placed on `Main Camera` manually) to `Camera.main`. Follows a target `Transform` (the player) in `LateUpdate`, clamped to the map's half-extent so the camera never shows outside the level; if the map is smaller than the screen on an axis, it centers on that axis instead of tracking.

### Story system

Galgame-style pre-battle dialogue, driven entirely by a plain-text script per level — deliberately **not** a `ScriptableObject`/Inspector-row format, specifically so someone without Unity access can author it. Purely linear (no branching/choices — the game is PVE-focused; story exists to flesh out worldbuilding, not to be the main loop).

- `Assets/Script/Story/StoryStep.cs` — the parsed-out data model: `StoryStepType` (`Background`/`Bgm`/`Enter`/`Exit`/`Say`/`Middle`/`Wait`) + a flat `StoryStep` struct carrying whichever fields that type needs (`Side`, `CharacterId`, `Expression`, `Text`, `BackgroundName`, `AudioClipName`, `Duration`).
- `Assets/Script/Story/StoryScriptParser.cs` — a static `Parse(string) -> List<StoryStep>`. Script syntax: non-`#` lines are dialogue text (attributed to whichever side the most recent `#speak` set); `#`-prefixed lines are commands — `#bg <name>`, `#bgm <clipName>` (plays via `AudioManager.PlayBGM`, so it's a no-op if that clip is already playing), `#enter <left|right> <characterId> <expression>`, `#exit <left|right>`, `#speak <left|right|none>`, `#middle <text>`, `#wait <seconds>` (pauses playback without needing a click — for beats that just need a pace-setting delay); `//`-prefixed lines are comments, blank lines are ignored. Unknown/malformed commands log a warning and are skipped rather than throwing, so one bad line in a non-programmer-authored script doesn't halt parsing. Extending the format means adding a new `case` here, not redesigning anything.
- `Assets/Script/Story/StoryManager.cs` — the `Story.unity` scene entry point. Reads `levelData.preBattleStoryScript` in `Awake()` (parsed once), then in `Start()` snapshots the scene's initial UI state (background color, left/right character rest positions) before driving playback via a single coroutine that walks the step list. `levelData` is currently a hardcoded `[SerializeField]` (same placeholder pattern as `LevelManager.difficulty`) until a level-select flow exists to pass it in dynamically. Key behaviors:
  - **Advance model**: click anywhere not over UI (`EventSystem.current.IsPointerOverGameObject()` gates it — see the raycast-target note below) — if the current line is still typewriter-animating, the click instantly completes it; if already complete, it advances to the next step. `Enter`/`Exit`/`Background`/`Bgm`/`Wait` steps play automatically with no click needed; only `Say`/`Middle` steps pause for input.
  - **Speaker dimming**: automatic — whichever side a `Say` step's `Side` points at gets `activeSpeakerColor`, the other gets `dimmedSpeakerColor`; narration (`Side: None`) dims both.
  - **`Middle` steps**: fade the actual `BackGround` `Image.color` to black and the dialogue box (`Down`, via a runtime-added `CanvasGroup`) to alpha 0, together, over `middleFadeDuration`, *before* the middle text starts typing — then reverse both together on dismiss. No separate overlay object; it repurposes the existing background.
  - **Auto-play**: a toggle button, visible from the very first viewing, that does **not** persist across scene entries (always starts off). When on, a completed line auto-advances after `autoPlayDelay` seconds instead of waiting for a click — applies to `Middle` steps too. A manual click during the wait just advances early without turning auto-play off.
  - **Skip button**: only shown if this level's story has been fully viewed before (see persistence below); jumps straight to `CompleteStory()`, bypassing whatever remains.
  - **Persistence**: `PlayerPrefs` keyed by `"Story_Seen_" + levelData.levelId`, set only once the *entire* script has played through (or been skipped) — there's no mid-script checkpoint, matching the level-select design where a level is either "never seen" (auto-plays, no skip button) or "seen" (skip offered).
  - **Portrait/background art**: resolved by name via `Resources.Load<Sprite>("Images/Characters/{characterId}/{expression}")` / `"Images/BackGround/{name}")` — no Inspector wiring needed per asset, mirroring `AudioManager`'s `Resources.Load`-by-name convention so new art just needs to be dropped in the right folder.
  - On completion (natural end or Skip), marks the level's story as seen and calls `SceneManager.LoadScene("Battle")` — currently unconditional, since there's no level-select flow yet to decide otherwise.
  - Like `PauseMenuUI`/`UIManager`, all UI references (`backgroundImage`, `leftCharacterImage`, `downRoot`, buttons, etc.) are Inspector-wired to the existing `Story.unity` hierarchy (`BackGround`/`Down`/`LeftCharacter`/`RightCharacter`/`CharacterName`/`Dialogue`/`Middle`/`MiddleText`) — this script generates no UI itself. The Auto-play/Skip buttons don't exist in the scene yet and need to be added and wired manually — **they must live outside `backgroundImage`/`downRoot`/`middleRoot`'s hierarchy** (e.g. as siblings directly under the `UI` canvas), since `Start()` disables `raycastTarget` on every `Graphic` under those three roots so that click-anywhere-to-advance isn't swallowed by the full-screen background/dialogue-box graphics; a button nested inside one of them would become unclickable.

When adding a new level's pre-battle story, write a `.txt` script using the syntax above, assign it as a `TextAsset` to that level's `LevelData.preBattleStoryScript`, and give the `LevelData` a unique `levelId`. Character/background art referenced by the script must exist under `Assets/Resources/Images/Characters/{id}/{expression}.png` / `Assets/Resources/Images/BackGround/{name}.png` — the `characterId` string doubles as both the folder name and the on-screen speaker name.

### UI

- `Assets/Script/UI/UIManager.cs` — polls `PlayerBase` (found via `Player` tag) and `LevelManager.Instance` every `Update()` and pushes state into UI `Image`/`Text` fields wired in the Inspector: heart (health bar + color-graded by ratio), skill cooldown ring, ultimate ring, and the enemy-pool health bar/name (via `LevelManager.EnemyGroupHealthRatio`/`LevelName` — not any single enemy). Read-only — it never mutates gameplay state. `UpdateS2()` reads the character-agnostic `S2_CooldownCurrent`/`S2_Cooldown` pair off `PlayerBase` (see `PlayerBase.S2_ShowSecondsFormat` above) and branches its text format: charge-style characters (SuperCat) render `"{current}/{max}"`, pure-cooldown characters (RedSuperCat) render remaining seconds instead — the fill-ring math itself doesn't need to branch, only the label. Its lookups run in `Start()`, not `Awake()`, specifically because `LevelManager` instantiates the player/enemies inside its own `Awake()`, and Unity does not guarantee `Awake()` order between different GameObjects — only that every object's `Awake()` finishes before any object's `Start()` begins.
  - **Per-character skill icons**: each skill slot's UI (`Skill 1`/`Skill 2` in `Battle.unity`) is a `Disk` (static frame) with an `Icon` (dim background layer) and an `IconMask` (bright radial-fill overlay, the same `Image` already wired as `S1_FillImage`/`S2_FillImage`) both showing the identical sprite. `PlayerBase` exposes that sprite per-character via `[SerializeField] Sprite s1Icon/s2Icon` (set per character prefab in the Inspector) and read-only `S1_Icon`/`S2_Icon` properties; `UIManager.SetupSkillIcons()` (called once from `Start()`, not every frame — icons never change mid-battle) pushes them into both `S1_IconImage`/`S2_IconImage` (the dim `Icon` layer) and the existing `S1_FillImage`/`S2_FillImage` (the `IconMask` layer). If a character prefab leaves `s1Icon`/`s2Icon` unassigned, `SetupSkillIcons()` leaves whatever sprite is already on those `Image`s in the scene untouched rather than overwriting it with null.
  - **Enemy health bar's delayed white drain**: `enemyFillImage` (red) always snaps to `LevelManager.EnemyGroupHealthRatio` immediately; `enemyWhiteFillImage`, layered behind it, is a separate small state machine (`Idle`/`Waiting`/`Draining`) that only starts catching down `enemyWhiteDelay` seconds after a drop, then `Lerp`s down to the new ratio over `enemyWhiteDrainDuration` — a "damage trail" effect. A second drop arriving mid-drain restarts the `Lerp` from the white bar's *current* position rather than resetting the delay, so rapid hits don't stall the white bar. There's no enemy-heal case handled specially since enemies don't currently regen — a ratio *increase* just snaps both bars instantly.
- `Assets/Script/UI/BattleResultUI.cs` — the win/lose results screen; polls `PlayerBase.IsDead`/`LevelManager.LevelCleared` every `Update()` (mirrors `UIManager`'s `Start()`-not-`Awake()` lookup timing) and fires exactly one of two coroutines the first time either flips true. Both sequences: pause enemy AI (`LevelManager.PauseAllEnemies(true)`), stop the BGM and play a result SFX, slide the HUD (health-bar/status groups) off-screen, slide a shared "result text" label in from the top (`"完全勝利"`/`"慘敗..."`, recolored per outcome), then — no earlier than `DetailsRevealDelay` seconds after the sequence started, regardless of how long the animation up to that point actually took (`WaitUntilElapsedSince`) — reveal a shared info box and a "return to lobby" button (`OnReturnToLobby` just `Debug.Log`s for now; no lobby scene exists yet). They diverge in a few ways: victory additionally freezes the player as invulnerable-but-mobile (`SetForcedInvincible(true)` + `SetSuppressNormalAttack(true)`) and walks through one `ShowInfoBoxUntilClicked` per entry in `victoryRewards` (a hardcoded placeholder list — no save/reward system wired up yet), each dismissed by a click that isn't over UI; defeat instead freezes the camera (`CameraFollow.Freeze()`), moves the player to a camera-relative death pose via `PlayerBase.BeginDeathSequence`, and spawns a runtime-generated black `SpriteRenderer` (`PlaceholderSprite`, same temp-art convention as `Bullet`/`SmokePuff`) to darken the screen — sorted above every other sprite except the player's own (bumped to a higher `sortingOrder` so it isn't darkened out), and shows one persistent info box reporting the enemy pool's remaining health % instead of a click-through reward list. Like `StoryManager`, it disables `raycastTarget` on every `Graphic` under the result-text/info-box roots in `Start()` so "click anywhere" during the reward loop isn't swallowed by their own full-screen graphics. All widgets are Inspector-wired (same manual style as `UIManager`/`PauseMenuUI`); the only thing generated at runtime is the darken layer.
- `Assets/Script/UI/PauseMenuUI.cs` — Esc-toggled pause/settings panel: freezes battle via `Time.timeScale = 0` (BGM keeps playing since it isn't scaled) and lets the player change windowed resolution (from a fixed 16:9 preset list, filtered down to whatever fits the screen's native resolution) or toggle fullscreen (`FullScreenMode.FullScreenWindow` at native resolution). Settings are persisted to `PlayerPrefs` and only auto-applied on next launch if a value was previously saved (a fresh install keeps the Player Settings default rather than forcing a resolution). Applying settings reloads the active scene so `LevelManager.Awake()` recomputes walls/background/camera bounds for the new aspect ratio — those are computed once at scene load and don't otherwise track resolution changes. Like `UIManager`, all panel widgets (`Panel`/`Dropdown`/`Toggle`/`Button`) are wired manually in the Inspector rather than generated in code.

### Shared/common

- `Assets/Script/Common/AudioManager.cs` — global singleton (`AudioManager.Instance`), auto-created on first access and marked `DontDestroyOnLoad`; no need to place it in the scene manually. Loads clips lazily from `Resources.Load<AudioClip>("Audio/SFX/{name}")` / `"Audio/BGM/{name}"` (see `Assets/Resources/Audio/SFX|BGM/`) and caches them by name. `PlayBGM`/`PlaySFX` accept either a clip name (string) or an `AudioClip` directly; `PlayBGM` no-ops if the same clip is already playing; `PlaySFX` uses `PlayOneShot` so multiple SFX can overlap. `PlayRandomHurtSfx()` is the shared "hurt1"/"hurt2" hit sound used by both `PlayerBase.TakeDamage` and `EnemyBase.TakeDamage`. Any new gameplay code that plays audio should go through this singleton rather than adding its own `AudioSource`.
- `Assets/Script/Common/CameraFollow.cs` — see "Level framework" above; attached to `Camera.main` at runtime by `LevelManager`, not placed in the scene manually.
- `Assets/Script/Common/KnockbackState.cs` — a plain (non-`MonoBehaviour`) class implementing the actual knockback displacement: `TryApply(direction, distance, duration)` starts it (rejected if already mid-knockback), and the owner's `FixedUpdate()` must call `Tick(Time.fixedDeltaTime)` every physics step to move its `Rigidbody2D` and count down. Both `PlayerBase` and `EnemyBase` hold one via composition rather than sharing a base class, since they're separate inheritance chains (same pattern `ISkill` already uses elsewhere in this codebase). `IKnockbackable.TryKnockback` on each side is a thin wrapper that adds its own eligibility checks (`IsDead`, `CanBeKnockedBack`) and side effects (playing the `KB` animation for enemies, interrupting active skills for the player) before delegating here.
- `Assets/Script/Common/MeleeHitbox.cs` — a static helper for "stationary swing" melee attacks (as opposed to `ChargeRamSkill`'s "move the attacker's body into the target" style): `MeleeHitbox.Hit(origin, direction, offset, size, targetTag, damage, knockbackDistance)` does one immediate `Physics2D.OverlapBoxAll` at a box positioned `offset` units along `direction` from `origin` — no persisting trigger collider, so it can never double-hit the same target across frames. Hits everything under `targetTag`, calling `TakeDamage` and (if `knockbackDistance > 0`) `IKnockbackable.TryKnockback` on each. Not currently used by any skill — added so the melee attack framework supports both movement- and swing-style hits from day one; wire a new skill to it when one needs a stand-in-place attack.
- `Assets/Script/Common/Bullet.cs` — projectile spawned via the static `Bullet.Spawn(prefab, owner, origin, targetPosition, damage, targetTag, bulletType, onHit, speed, lifeTime, homingTarget, homingTurnRateDegrees, homingDuration)` factory (`owner` is a plain `MonoBehaviour`, not `PlayerBase`-only, so enemies can fire bullets too — the only player-specific behavior, granting +1 charge on hit, is gated by an `owner is PlayerBase` type check rather than baked into the type signature). `bulletType` through `homingDuration` are all optional with defaults matching the original plain-shot behavior; `onHit` is an `Action` the spawning skill can hook to run its own side effect on a hit or bullet-kill (e.g. `RedSuperCat`'s passive cooldown reduction). Flies in a straight line by default, damages colliders tagged `targetTag` (explicitly passed per spawn, e.g. `"Enemy"` for player-fired bullets — not inferred from `owner`, so a future summon-type attacker can still target either side), and is destroyed on hitting `targetTag` or `Wall`. Passing a non-null `homingTarget` (plus `homingTurnRateDegrees`/`homingDuration`) makes the bullet steer toward that `Transform` at a capped turn rate (`Vector3.RotateTowards` on the direction vector) each `FixedUpdate` until `homingDuration` elapses, after which it reverts to straight-line flight in whatever direction it was last facing — used by `RadialBurstSkill`'s tracking shots (mild homing) vs. `ChargeRamSkill`'s own unrelated dash-homing logic (unrelated system, don't conflate the two). `BulletType` (`Normal`/`Destructive`/`Immune`) governs bullet-vs-bullet interaction, detected via `TryGetComponent<Bullet>` on whatever it overlaps (no dedicated "Bullet" tag): the entire interaction matrix collapses into one symmetric rule evaluated independently by each bullet — "if I'm `Destructive` and the other bullet isn't `Immune`, destroy it" — which naturally produces mutual destruction between two `Destructive` bullets (each destroys the other) without any special-cased pairwise logic; bullets sharing the same `targetTag` (e.g. two of the 20 bullets from one `RadialBurstSkill` volley, both tagged `"Enemy"`) never affect each other regardless of type, so a volley can't self-destruct on spawn. Falls back to a runtime-generated placeholder visual if no prefab is supplied.
- `Assets/Script/Common/SmokePuff.cs` — a scale-up/fade-out hit-effect placeholder that self-destructs after `lifeTime`.
- `Assets/Script/Common/PlaceholderSprite.cs` — generates and caches solid-color 1×1-world-unit square sprites, used by scripts (`Bullet`, `SmokePuff`, `BattleResultUI`'s defeat-screen darken layer) as a stand-in visual whenever no art prefab/sprite has been assigned yet. Prefer wiring real prefabs/sprites when art is available rather than relying on this permanently.

Collision/trigger logic throughout depends on GameObject tags: `Player`, `Enemy`, and `Wall` — make sure new prefabs are tagged correctly for damage and collision interactions to work.

## Asset layout

- `Assets/Resources/Images/Characters/`, `Assets/Resources/Images/Enemys/`, `Assets/Resources/Images/BackGround/`, `Assets/Resources/Images/Effects/`, `Assets/Resources/Images/UI/` — sprite assets, organized by category/entity name (e.g. `Enemys/1_Doge/`). All of `Assets/Images/` lives under `Resources` now (moved there for the Story system's `Resources.Load<Sprite>` lookups — see "Story system" above); most of these subfolders (`Enemys`, `Effects`, `UI`) are still only ever referenced via direct Inspector/prefab/Animator wiring, not loaded by name — only `Characters/` and `BackGround/` are actually read via `Resources.Load` (by `StoryManager`).
- `Assets/Resources/Audio/SFX/` and `Assets/Resources/Audio/BGM/` — audio clips loaded by name at runtime through `AudioManager` (via `Resources.Load<AudioClip>("Audio/SFX|BGM/{name}")`); a new clip just needs to be dropped in the matching folder and referenced by filename (no extension) from code.
- `Assets/Animator/` — Animator Controllers and clips per character (e.g. `Animator/SuperCat/`, `Animator/RedSuperCat/`, `Animator/Doge/`), matching the animation trigger names used in code (`KB`, `OpenMouth`, `CloseMouth`). `Assets/Animator/Effects/` holds the debuff-icon Animator Controllers/clips (`CurseIcon`, `SlowIcon`, `Smoke`, etc.) referenced by `debuffIconPrefab` children — see "Debuff / crowd-control system" above.
- `Assets/Prefabs/` — playable/enemy/projectile/effect prefabs: `SuperCat.prefab`, `RedSuperCat.prefab`, `1_Doge.prefab`, `Bullet.prefab`, `RedBullet.prefab`, `SonicWave.prefab` (despite the name, this now just carries a plain `Bullet` component — the old `SonicWave` `MonoBehaviour` was deleted, see "Enemies" above), `Smoke.prefab`, `BuffDisplay.prefab` (a `DebuffIconDisplay` instance, wired as the default `debuffIconPrefab`).
- `Assets/Scenes/Battle.unity` — the main combat scene, driven by `LevelManager` as described above. `Assets/Scenes/Story.unity` is the pre-battle dialogue scene, driven by `StoryManager` (see "Story system" above). Both scenes are registered in `ProjectSettings/EditorBuildSettings.asset`.
- `Assets/Script/Editor/BattleCatsImport/` — a Unity Editor tool (`Tools > Battle Cats Import > Import Model From PNG...`, `BcModelImporterWindow.cs`/`BcFormat.cs`) that converts Battle-Cats-ripped native art (`xxx.png` + `xxx.imgcut` + `xxx.mamodel` + `xxx0N.maanim`, extracted via an external BCU tool — not part of this repo) into a Unity part-hierarchy prefab plus `AnimationClip`s, so new enemy/character art can be brought in without manually rebuilding rigs by hand. Used to bring in the `2_PhotoCat` enemy art (`Assets/Images/Enemys/2_PhotoCat/`). Generated rigs need `Assets/Script/Common/BcRigNode.cs` on each part node — the source format's opacity multiplies down the parent chain, which Unity's independent `SpriteRenderer`s don't do on their own, so `BcRigNode.EffectiveAlpha` recomputes the multiplied alpha every `LateUpdate` (`[ExecuteAlways]`, so it also updates while scrubbing an `AnimationClip` in the Editor outside Play mode). Full player-character rig import (not just static enemy parts) is still a work in progress as of the `charAnim` commit — expect rough edges if extending this tool for a new playable character's rig.

Comments in source are written in Traditional Chinese (zh-TW); match this convention when editing existing files with Chinese comments.
