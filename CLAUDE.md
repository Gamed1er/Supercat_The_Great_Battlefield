# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A Unity 2D game project (working title "超人貓大亂鬥" / "Super Cat Brawl"). Unity Editor version **2022.3.62f3**. The project has a working combat loop: one playable character (SuperCat) with three functioning skills, and one enemy (DogeEnemy) with a three-difficulty, two-phase attack pattern, playable in `Assets/Scenes/Battle.unity`.

## Development environment

This is a Unity project, not a CLI-buildable package — there are no npm/dotnet CLI build, lint, or test commands to run from the terminal. Building, running, and testing happen inside the Unity Editor:

- Open the project via Unity Hub with Editor version `2022.3.62f3` (see `ProjectSettings/ProjectVersion.txt`).
- Play mode in the Editor (on `Assets/Scenes/Battle.unity`) is the primary way to run and manually test the game.
- The `com.unity.test-framework` package is installed, so Unity Test Runner (Window > General > Test Runner) is available for EditMode/PlayMode tests, but no test assemblies exist yet.
- C# scripts target `netstandard2.1` / `LangVersion 9.0` (see `Assembly-CSharp.csproj`). The `.sln`/`.csproj` files are Unity-generated — treat them as build artifacts, not hand-maintained project files.
- Do not edit files under `Library/`, `Temp/`, `Logs/`, `UserSettings/`, or `obj/` — these are Unity-generated caches, not source.

## Code architecture

Gameplay scripts live under `Assets/Script/`, split into `Player/`, `Enemy/`, `Level/`, `UI/`, and `Common/`.

### Stats/skill composition pattern (players)

- `Assets/Script/Player/PlayerBase.cs` — `PlayerBase : MonoBehaviour, IDamageable, IKnockbackable` is the shared base for all playable characters. Requires `Rigidbody2D`, `CircleCollider2D`, `SpriteRenderer`, `Animator`. It holds a `PlayerStats` instance and three skill slots (`normalAttack`, `dashSkill`, `ultimateSkill`), each typed as `ISkill`. `Update()` reads WASD movement input, tracks `FacingDirection`, flips the sprite, and (unless `IsKnockedBack`) drives all three skills' `TryExecute()` every frame; `FixedUpdate()` applies movement (unless a skill is mid-movement via `IsActive`, or the player is `IsKnockedBack`), ticks dash/ultimate, and ticks the shared `KnockbackState` (see `EnemyBase`/"Shared/common" for what that is). Wall collisions call `Interrupt()`; enemy collisions call `OnHitEnemy()` on both movement skills. `CanBeKnockedBack => !ultimateSkill.IsActive` gates both `TakeDamage` (0 multiplier while true) and `TryKnockback` — the ultimate's dash invulnerability deliberately blocks knockback too, not just damage. A successful `TryKnockback` interrupts `dashSkill`/`ultimateSkill` the same way a wall hit does, so an incoming knockback always wins over an in-progress skill move. Also exposes read-only properties (`Health`, `MaxHealth`, `DashCooldown(Remaining)`, `UltimateCharge`/`UltimateMaxCharge`) purely for `UIManager` to bind to.
- `ISkill` (defined in `Assets/Script/Player/Skills/SkillBase.cs`) is the contract every skill implements: `Cooldown`, `CooldownRemaining` (seconds until ready, for UI), `TryExecute()`, `IsActive`, `Tick()`, `Interrupt()`, `OnHitEnemy(Collider2D)`. Skills that involve a movement/dash phase (dash, ultimate) use `IsActive`/`Tick()`/`Interrupt()`/`OnHitEnemy` to drive their own `Rigidbody2D.MovePosition` during `FixedUpdate` while suppressing normal WASD movement; instant-effect skills (normal attack) implement these as no-ops. Skills are independent, swappable classes (composition over inheritance) — a character is assembled by wiring concrete `ISkill` implementations into the base's skill slots in `Awake()`, not by subclassing behavior.
- `IDamageable` (defined in `PlayerBase.cs`) is the contract for anything that can take damage (`TakeDamage(float amount)`); implemented by both `PlayerBase` and `EnemyBase`. `IKnockbackable` (also in `PlayerBase.cs`) is the parallel contract for anything that can be pushed back (`TryKnockback(Vector2 direction, float distance)`); also implemented by both. Attack code should target these two interfaces rather than the concrete `PlayerBase`/`EnemyBase` types, so the same attack logic works regardless of which side is being hit.
- `PlayerStats` (also in `PlayerBase.cs`) is a plain data class holding `baseAttack`, `baseHealth`, `moveSpeed`, `Health`, and a shared **charge** resource (`Charge`, capped at the const `MaxCharge`) with `AddCharge`/`SpendCharge` — charge is spent by ultimates and earned via normal-attack hits (`Bullet` grants +1 on enemy hit).
- `Assets/Script/Player/SuperCat.cs` is the one implemented character: subclasses `PlayerBase`, and in `Awake()` wires up `AutoLockShootSkill` (normal attack), `DashSkill` (dash), and `ChargeRamSkill` (ultimate) — all under `Assets/Script/Player/Skills/`. Player-facing values (attack/health/moveSpeed) are currently hardcoded per-character in `Awake()` rather than driven by a leveling system.
- Skill implementations follow a click-toward-cursor convention: on mouse-button-down, direction is computed straight from the owner's position to the mouse's world position (via `Camera.main.ScreenToWorldPoint`) — there is no drag tracking. `DashSkill` triggers on left-click and is gated by a cooldown, and deals no damage (pure movement). `ChargeRamSkill` triggers on right-click, is gated by charge cost instead of a cooldown (`Cooldown => 0f`), and grants **full damage immunity** (`PlayerBase.TakeDamage` multiplies by `0f`) while `IsActive`; on hit it deals damage and also calls `IKnockbackable.TryKnockback` with the charge direction and a large knockback distance (a "movement-based" melee hit — the attacker's own body moves into the target, as opposed to a stationary hitbox swing; see `MeleeHitbox` below for that alternative). Both skills play SFX through `AudioManager` on trigger, on cooldown-block ("no"), and (dash) on cooldown-ready ("skill_done").

When adding a new playable character, follow the `SuperCat` pattern: subclass `PlayerBase`, and in `Awake()` assign concrete `ISkill` implementations to `normalAttack`, `dashSkill`, and `ultimateSkill`. When adding a new skill, implement `ISkill` as an independent class (not a `MonoBehaviour`) that takes the owning `PlayerBase` and its tuning parameters via constructor, matching the existing `AutoLockShootSkill(this, bulletPrefab, damageMultiplier: ...)` call-site style.

### Enemies

- `Assets/Script/Enemy/EnemyBase.cs` — shared base: `health`, `baseAttack`, `MaxHealth`/`HealthRatio` (captured from `health` in `Start()`, after difficulty has been applied), `IsDead`, `TakeDamage`, `IsKnockedBack`, `TryKnockback(Vector2 direction, float distance)` (fails if dead/`CanBeKnockedBack` returns false/already knocked back). Knockback/stagger state itself lives in a shared `KnockbackState` instance (composition, not inheritance — see "Shared/common" below) that both `EnemyBase` and `PlayerBase` hold independently; `EnemyBase.FixedUpdate()` ticks it every physics step, which is what actually moves the Rigidbody2D during the knockback window and counts down the stagger timer (sourced from the defender's own `knockbackDuration` field — the attacker only controls direction/distance, never how long the stagger lasts). Subclasses override `CanBeKnockedBack` to make specific attacks uninterruptible, must check `IsKnockedBack`/`IsDead` at the top of their own `Update()`/`FixedUpdate()` overrides, and **must call `base.FixedUpdate()`** in any `FixedUpdate()` override — skipping it silently breaks knockback displacement for that enemy. Also defines the shared `Difficulty` enum (`Easy`/`Normal`/`Hard`) and a virtual `ApplyDifficulty(Difficulty)` that sets `health`/`baseAttack` from three serialized `DifficultyStats` (health+attack) pairs configured per-prefab in the Inspector — deliberately absolute numbers, not a multiplier, so each enemy can have a hand-tuned (non-linear) difficulty curve. Subclasses override `ApplyDifficulty` to call `base.ApplyDifficulty(difficulty)` and then layer their own extra difficulty-scaled parameters on top. Also defines a virtual `SetGroundBounds(Vector2 min, Vector2 max)` for ground-walking enemies to store their wander/chase rectangle; enemies that don't need a floor (e.g. flying) can ignore it. Requires `Rigidbody2D` (kinematic, no gravity), `CircleCollider2D`, `SpriteRenderer`.
- `Assets/Script/Enemy/DogeEnemy.cs` subclasses `EnemyBase` and is the only enemy with real behavior: it wanders/chases within the rectangle set via `SetGroundBounds` (stored in the inherited `groundMin`/`groundMax` fields — `LevelManager` computes and assigns this at spawn time, see below) and cycles through attacks on a timer — a jump attack normally, or a horizontal "bite" (`BiteRoutine`) instead when the player is hiding below `biteThresholdY` where the jump's arc can't reach. Once health drops at/below `phase2HealthPercent` of max, it gains a second-phase "big bark" attack (`BigBarkRoutine`) that spawns a rotating `SonicWave` beam and is uninterruptible (`CanBeKnockedBack => !isBigBarking`) for its whole duration including repositioning. Its `ApplyDifficulty` override calls `base.ApplyDifficulty` (health/attack) then layers its own difficulty-scaled timings (`phase1CycleInterval`, `phase2CycleInterval`, `jumpDuration`, `bigBarkRotationSpeed`). Long attacks run as coroutines and set `isPerformingAction` to suspend wandering/attack-cycle logic while they play; contact damage against the player (covering bite, jump, and plain wandering collisions alike — there's no separate per-attack damage path) is handled in `OnCollisionStay2D`, rate-limited by `bodyContactDamageInterval`, and now also applies a minor knockback via `IKnockbackable.TryKnockback` using the horizontal-only direction from Doge to the player (`contactKnockbackDistance`) — vertical component is deliberately zeroed so a jump landing doesn't launch the player up/down.
- `Assets/Script/Enemy/SonicWave.cs` is a standalone `MonoBehaviour` (not an `ISkill`) representing the rotating beam hazard spawned by `DogeEnemy`'s phase-2 attack. It has a charge-up state (`Init`/`SetChargingVisual`, fades in without rotating or damaging) followed by an active sweep (`BeginSweep`) that rotates around a pivot transform and deals tick damage to anything tagged `Player` inside its trigger collider. This is an area attack and deliberately has no knockback — knockback in this codebase only ever comes from melee attacks.

New enemies should subclass `EnemyBase` the way `DogeEnemy` does, rather than implementing `IDamageable` directly. `ApplyDifficulty`/`SetGroundBounds` are called by `LevelManager` immediately after `Instantiate` (i.e. during `LevelManager.Awake()`), which is guaranteed to run before the new enemy's own `Start()` — never before its `Awake()` finishes.

### Level framework

- `Assets/Script/Level/LevelData.cs` — a `[CreateAssetMenu]` `ScriptableObject` holding everything that varies per level: `levelName` (shown as the enemy-group health bar's label), `mapWidthMultiplier`/`mapHeightMultiplier` (map half-extent = one "base" screen-sized half-extent × these — see `LevelManager.GetBaseHalfExtent()` below), `groundHeightPercent` (the bottom N% of the map counted as ground for `SetGroundBounds`), `playerSpawnPosition`, `enemyPool` (a `List<EnemySpawnEntry>`, each an enemy prefab + spawn position — spawned once, all at level start; no wave system yet), `bgmName`, and `backgroundTilePrefab`. Difficulty is deliberately **not** part of `LevelData` — the same level can be replayed at any difficulty, so it lives on `LevelManager` instead.
- `Assets/Script/Level/LevelManager.cs` — replaces the old `BattleManager`; it's the scene entry point for `Battle.unity` and does all level setup in `Awake()` (in order: reposition the four `Wall`-tagged boundary objects found via `GameObject.FindGameObjectsWithTag("Wall")` — classified as horizontal/vertical by comparing `|x|` vs `|y|`, only their position is changed since their colliders are already oversized (100 units) to cover any reasonable map size — then tile the background, then instantiate the player at `playerSpawnPosition`, then instantiate each `enemyPool` entry and call `ApplyDifficulty`/`SetGroundBounds` on it, then wire up the camera). `GetBaseHalfExtent()` derives "1 map multiplier unit" from `Camera.main.orthographicSize`/`aspect` at runtime rather than a hardcoded constant, so a multiplier of 1 always means exactly one screen's worth of space regardless of resolution/aspect ratio — do not reintroduce a fixed half-width/half-height constant here, it will silently drift from the real screen the moment aspect ratio changes. Exposes a static `Instance`, `LevelName`, and `EnemyGroupHealthRatio` (current pooled health ÷ the total health captured right after `ApplyDifficulty` at spawn time — a fixed denominator, so killing an enemy visibly drops the bar instead of the ratio re-basing itself). `Update()` checks whether every spawned enemy's `IsDead` is true and logs once when the level is cleared (no win/lose UI or scene transition yet — that's still to be built). Difficulty is a `[SerializeField] Difficulty` field on `LevelManager` itself, currently a placeholder manually set in the Inspector until a level-select/difficulty-select flow exists to pass it in.
- `Assets/Script/Common/CameraFollow.cs` — added at runtime by `LevelManager` (via `AddComponent`, so it never needs to be placed on `Main Camera` manually) to `Camera.main`. Follows a target `Transform` (the player) in `LateUpdate`, clamped to the map's half-extent so the camera never shows outside the level; if the map is smaller than the screen on an axis, it centers on that axis instead of tracking.

### UI

- `Assets/Script/UI/UIManager.cs` — polls `PlayerBase` (found via `Player` tag) and `LevelManager.Instance` every `Update()` and pushes state into UI `Image`/`Text` fields wired in the Inspector: heart (health bar + color-graded by ratio), skill cooldown ring, ultimate charge ring, and the enemy-pool health bar/name (via `LevelManager.EnemyGroupHealthRatio`/`LevelName` — not any single enemy). Read-only — it never mutates gameplay state. Its lookups run in `Start()`, not `Awake()`, specifically because `LevelManager` instantiates the player/enemies inside its own `Awake()`, and Unity does not guarantee `Awake()` order between different GameObjects — only that every object's `Awake()` finishes before any object's `Start()` begins.

### Shared/common

- `Assets/Script/Common/AudioManager.cs` — global singleton (`AudioManager.Instance`), auto-created on first access and marked `DontDestroyOnLoad`; no need to place it in the scene manually. Loads clips lazily from `Resources.Load<AudioClip>("SFX/{name}")` / `"BGM/{name}"` (see `Assets/Audio/Resources/SFX|BGM/`) and caches them by name. `PlayBGM`/`PlaySFX` accept either a clip name (string) or an `AudioClip` directly; `PlayBGM` no-ops if the same clip is already playing; `PlaySFX` uses `PlayOneShot` so multiple SFX can overlap. `PlayRandomHurtSfx()` is the shared "hurt1"/"hurt2" hit sound used by both `PlayerBase.TakeDamage` and `EnemyBase.TakeDamage`. Any new gameplay code that plays audio should go through this singleton rather than adding its own `AudioSource`.
- `Assets/Script/Common/CameraFollow.cs` — see "Level framework" above; attached to `Camera.main` at runtime by `LevelManager`, not placed in the scene manually.
- `Assets/Script/Common/KnockbackState.cs` — a plain (non-`MonoBehaviour`) class implementing the actual knockback displacement: `TryApply(direction, distance, duration)` starts it (rejected if already mid-knockback), and the owner's `FixedUpdate()` must call `Tick(Time.fixedDeltaTime)` every physics step to move its `Rigidbody2D` and count down. Both `PlayerBase` and `EnemyBase` hold one via composition rather than sharing a base class, since they're separate inheritance chains (same pattern `ISkill` already uses elsewhere in this codebase). `IKnockbackable.TryKnockback` on each side is a thin wrapper that adds its own eligibility checks (`IsDead`, `CanBeKnockedBack`) and side effects (playing the `KB` animation for enemies, interrupting active skills for the player) before delegating here.
- `Assets/Script/Common/MeleeHitbox.cs` — a static helper for "stationary swing" melee attacks (as opposed to `ChargeRamSkill`'s "move the attacker's body into the target" style): `MeleeHitbox.Hit(origin, direction, offset, size, targetTag, damage, knockbackDistance)` does one immediate `Physics2D.OverlapBoxAll` at a box positioned `offset` units along `direction` from `origin` — no persisting trigger collider, so it can never double-hit the same target across frames. Hits everything under `targetTag`, calling `TakeDamage` and (if `knockbackDistance > 0`) `IKnockbackable.TryKnockback` on each. Not currently used by any skill — added so the melee attack framework supports both movement- and swing-style hits from day one; wire a new skill to it when one needs a stand-in-place attack.
- `Assets/Script/Common/Bullet.cs` — projectile spawned via the static `Bullet.Spawn(prefab, owner, origin, targetPosition, damage, targetTag, bulletType)` factory (`owner` is a plain `MonoBehaviour`, not `PlayerBase`-only, so enemies can fire bullets too — the only player-specific behavior, granting +1 charge on hit, is gated by an `owner is PlayerBase` type check rather than baked into the type signature). Flies in a straight line locked at spawn time, damages colliders tagged `targetTag` (explicitly passed per spawn, e.g. `"Enemy"` for player-fired bullets — not inferred from `owner`, so a future summon-type attacker can still target either side), and is destroyed on hitting `targetTag` or `Wall`. `BulletType` (`Normal`/`Destructive`/`Immune`) governs bullet-vs-bullet interaction, detected via `TryGetComponent<Bullet>` on whatever it overlaps (no dedicated "Bullet" tag): the entire interaction matrix collapses into one symmetric rule evaluated independently by each bullet — "if I'm `Destructive` and the other bullet isn't `Immune`, destroy it" — which naturally produces mutual destruction between two `Destructive` bullets (each destroys the other) without any special-cased pairwise logic. Falls back to a runtime-generated placeholder visual if no prefab is supplied.
- `Assets/Script/Common/SmokePuff.cs` — a scale-up/fade-out hit-effect placeholder that self-destructs after `lifeTime`.
- `Assets/Script/Common/PlaceholderSprite.cs` — generates and caches solid-color 1×1-world-unit square sprites, used by scripts (`Bullet`, `SonicWave`, `SmokePuff`) as a stand-in visual whenever no art prefab/sprite has been assigned yet. Prefer wiring real prefabs/sprites when art is available rather than relying on this permanently.

Collision/trigger logic throughout depends on GameObject tags: `Player`, `Enemy`, and `Wall` — make sure new prefabs are tagged correctly for damage and collision interactions to work.

## Asset layout

- `Assets/Images/Characters/`, `Assets/Images/Enemys/`, `Assets/Images/BackGround/`, `Assets/Images/Effects/` — sprite assets, organized by category/entity name (e.g. `Enemys/1_Doge/`).
- `Assets/Animator/` — Animator Controllers and clips per character (e.g. `Animator/SuperCat/`, `Animator/Doge/`), matching the animation trigger names used in code (`KB`, `OpenMouth`, `CloseMouth`).
- `Assets/Prefabs/` — playable/enemy/projectile/effect prefabs: `SuperCat.prefab`, `1_Doge.prefab`, `Bullet.prefab`, `SonicWave.prefab`, `Smoke.prefab`.
- `Assets/Scenes/Battle.unity` — the only scene currently in the project.
- `Assets/Audio/Resources/SFX/` and `Assets/Audio/Resources/BGM/` — audio clips loaded by name at runtime through `AudioManager` (via `Resources.Load`); a new clip just needs to be dropped in the matching folder and referenced by filename (no extension) from code.
